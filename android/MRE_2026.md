Stan na 26 października 2026: implementacja i opisany odbiór lokalny ukończone przez O2.
Gałąź `codex/android-o2-mre-2026`, przekazanie O1 `e73f358`,
zwykły merge main `2d7fb073`. Zdalne CI i odbiór main pozostają osobnymi krokami.
Room pozostaje w wersji 27 (55 encji); import nie zmienia schematu ani starych posiłków.

## Dane i pochodzenie

Źródłem są materiały [MRE](../Random%20Data/MRE/README.md) zebrane 9 października 2026:
24 menu DLA / XLVI oraz 114 profili HPRC COMRAD. Oryginałów nie modyfikujemy.
Generator `tools/catalog/build_mre_2026.py` tworzy odtwarzalny pakiet w
`android/app/src/main/assets/catalog/mre2026/`. Zawiera oryginalny JSON,
manifest/hash/gzip E2 i reguły wyboru przywiązane do konkretnych rewizji racji.

To osobny pakiet referencyjny **demo**, release 1, package_id
`3aa9b766-b01d-5111-8fd0-4c5b6257961b`: 111 produktów, 24 racje,
235 komponentów i 112 źródeł. Dotychczasowy E2 DEMO 1 pozostaje niezależny:
18 produktów i 1 racja, bez zmiany ID, rewizji lub jego pliku gzip.
Razem z 15 produktami i 2 racjami legacy aplikacja ma 144 produkty i 27 racji.
Pozostałych trzech profili nie dodano bez powiązania z potwierdzoną pozycją.
Nie jest to oficjalny seed ARPOL / FDC z WYMAGANIA_PROJEKTOWE.md 11.4;
jego wymaganych etykiet i identyfikatorów FDC ten etap nie zastępuje.

SHA-256 kopii JSON źródła w APK (wyłącznie CRLF → LF, oryginał bez zmian):
`f519ef7390287c06293e7d45ff65371d5fa5cc68565994c948baebd2b0c2ad94`.
Gzip niezależnego wydania 1:
`2c0a1ff730e408cc90ab1fcfcb2b9eef21ebce8fa2d935d429f296d225260880`,
27 924 B. Payload: 246 314 B, SHA-256
`0552172f59de3f71597074b88dcb99c22d8c227eba7cb3ce96ac30f3e0a9d967`.
Transport jest identyczny z eksportem PostgreSQL: racje są sortowane po UUID
i rewizji, payload/manifest kończą się LF, gzip nie ma nazwy ani czasu i ma
OS = 255 (unknown). Hash każdej racji nadal dotyczy kanonicznego JSON bez LF.
Historyczny pin przekazania opisywał jeszcze plik WIP.
Wartości / 100 g są wyprowadzane z porcji COMRAD przez Decimal, ROUND_HALF_UP,
do 6 miejsc po przecinku. Źródłowa porcja i wszystkie 36 pól pozostają dostępne.
Masa porcji nie staje się liczbą sztuk; woda do proszków nie dodaje energii.
Źródłowy JSON COMRAD ma liczby dziesiętne. Lokalny ograniczony adapter
zachowuje ich oryginalny zapis jako tekst przed walidacją JSON; sprawdza
UTF-8, duplikaty, składnię i zagnieżdżenie. Parser protokołu E2 nadal
wymaga wartości dziesiętnych jako tekstów. Hash dotyczy oryginalnych bajtów.
Test w istniejącym zestawie `backend/tests/unit` odtwarza cztery artefakty
generatora i sprawdza stałe hashe, identyfikatory oraz liczności.

## Zachowanie aplikacji

- Po pierwszym uruchomieniu import odbywa się lokalnie, bez konta i API.
  Stary kompletny katalog pozostaje używalny przy błędzie nowego pakietu.
  MRE zapisane wcześniej bez dostępnych reguł nie pozwala zapisać niezweryfikowanego wyboru.
- Wybór wariantu odznacza pozostałe warianty tego samego składnika.
  Zaznaczenie zbiorcze omija nierozstrzygnięte warianty i starszą średnią
  pakietu dodatków. Repozytorium również odrzuca sprzeczny wybór.
- Średnia pakietu B z MRE 42 ma jawne oznaczenie. Nie jest dodawana do
  wybranych osobno składowych tego pakietu. Braki soli/gumy i pięć
  niepotwierdzonych dopasowań nie dostają wartości podobnego produktu lub zera.
- Użytkownik może zapisać niepotwierdzony składnik jako osobny ręczny wpis:
  podaje masę, a wartości / 100 g są opcjonalne. Puste pola oznaczają brak,
  jawne 0 jest znanym zerem. Zapis nie publikuje produktu ani nie nadaje mu
  tożsamości katalogowej. Brak kcal utrzymuje niekompletność dnia.
- Taki zapis pozostawia użytkownika przy wyborze racji i zachowuje inne
  zaznaczenia; jego własne makra i masa są trwale zapisane w dzienniku/kolejce.
  Wybór średniej pakietu zostaje odznaczony przed ręcznym dodawaniem.
- Znane składniki zachowują standardowe snapshoty katalogu, ilości i źródła.
  Etykiety/profil COMRAD, warianty, ograniczenia oraz brakujące dane są
  widoczne offline. Akcesoria niejadalne nie mają akcji zapisu do dziennika.

## Integracja i granice

Protokół E2 / sync-v1 nie został zmieniony. Niezależny odbiór scratch PostgreSQL 17
potwierdził import 111 produktów / 24 racji / 235 komponentów / 112 źródeł,
sync/read rzeczywistych niezmienionych wire
Kotlina, rozróżnienie ręcznego null oraz idempotencję bez duplikatów. Rzeczywiste
pliki eksportu PG gzip/manifest są bajtowo identyczne z generatorem, assets
i oboma APK. API używało syntetycznego Verifier; bez Keycloak / PKCE, TLS,
wdrożenia, publikacji lub aktywacji kanału official.

Operator O3 musi zaimportować **to samo wydanie MRE przed pierwszym rzeczywistym
account push** jego nowych referencji. Push przed importem zapisuje trwałą
odmowę `dependency_missing`; późniejszy import nie naprawia replay tego samego
UUID operacji. Obowiązują [komendy validate/import](../backend/README.md#e2-kontrolowany-import-eksport-i-publikacja)
dla właściwego wejścia MRE, bez kroku `publish`. Import należy uzgodnić poza
zamrożoną próbą Room 23 / E4. Trwający odbiór
`2319357` / Room 23 i jego cztery APK pozostają osobnymi, niezmienionymi artefaktami.
Nowy pakiet demo nie jest automatycznie kanałem official aktualizacji HTTPS.

## Odbiór lokalny O2

- Zbudowano debug, validation i test APK. Lint kodu etapu: 0 Error / 0 Fatal.
  `MreRationSelectionTest` (4 JVM) na końcowym pakiecie: 0 FAIL / 0 ERROR / 0 SKIP.
  Przypadki obejmują 24 hashe
  racji, warianty, niezależny przykład średnia/szczegóły, dokładne liczby
  źródła, Unicode oraz brak wartości odróżniony od jawnego zera.
- Poprawiono odczyt surowych liczb COMRAD i zgodność kanonizacji MRE między
  Androidem, JVM i Pythonem. Publiczny parser E2 zachował swoje ograniczenia.
  Zadania JVM deklarują teraz `catalogAssets` jako wejście względne:
  zmiana pakietu nie może pozostawić starego wyniku `UP-TO-DATE`.
- Pierwszy zakres 13 native miał 12 PASS i 1 FAIL nieprzenośnej asercji tekstu
  JSON. Sprawdzenie dokładnego pola po dekodowaniu zastąpiło substring;
  snapshot nadal jest porównywany bajtowo przed/po restarcie. Ponowiono ten
  przypadek oraz 4 zmienione fixture E2: łącznie 17 unikalnych PASS bez pominięć
  dla poprzedniego transportu. Po ujednoliceniu z eksportem PG uruchomiono
  na nowym ID tylko `MreCatalogueFlowTest` (3), `MreRationScreenTest` (1)
  i dodatkową regresję `CatalogMealStorageTest` (1):
  5 PASS / 0 FAIL / 0 ERROR / 0 SKIP. Pozostałe wyniki zachowują
  swój wcześniejszy zakres; pełne zdalne CI nadal jest wymagane.
- Końcowy APK zawiera rzeczywiste pliki eksportu PG, po ścisłym porównaniu
  z generatorem. Generator jest wykonywany w istniejącym zestawie
  `backend/tests/unit`; odtworzenie czterech artefaktów i Ruff mają PASS.
- Końcowa próba UI offline obejmuje 113,5 g chili / 145 kcal, zmianę wariantu
  menu 9, źródła COMRAD, ręczne 2,5 g z pustą energią i zachowanie zaznaczenia.
  Po force-stop / cold-start rzeczywisty ekran główny pokazuje 3 oczekujące
  wpisy, znaną część ≥ 442 kcal i 1 brak energii. Wszystkie wiersze 3 posiłków,
  3 składników i 3 operacji pozostają identyczne; osobny poprzedni profil
  z 6 wpisami zachowano bez zmiany DB / WAL / SHM. Nie kasowano danych profili.

za dowód wyglądu. Po jego usunięciu zebrano odrębne, sprawdzone kadry;
nie zmieniano z tego powodu kodu aplikacji. Konta testowe są syntetyczne.
Ten zakres nie potwierdza live OIDC / PKCE, Gemini ani pełnego odbioru 1.0.
