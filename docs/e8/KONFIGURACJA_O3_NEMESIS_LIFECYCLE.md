# Konfiguracja Nemesis lifecycle dla O3 - osoba 2

12 października 2026. E8.3-C ma własny pakiet i migration-owned SQL; produkcyjne main/health/provision/restore/purge nadal należą do zwolnionej później fazy I. Te instrukcje nie potwierdzają wykonania O3, wdrożenia lub aktywacji E8.4.

Aktualna nieopublikowana 0018_e8_nemesis_lifecycle rozszerza odebraną granicę upstream 0017_e8_purge_commit z b2c6709 po 0016_e8_motivation. Wcześniejsze próby 0016→0017 Nemesis są wyłącznie prototypem, nie odbiorem tej nowej linii. Migracja nie importuje zmiennego runtime. Koordynator potwierdził finalny numer/parent i przyjął dokładny source b2c6709 przed pierwszym pushem. Pusta i wypełniona linia wymaga rzeczywistej próby PG17. Downgrade z historią, minimalnymi receipts, admissions, codes, slots lub cursor odmawia atomowo przed DDL. Nie usuwamy tych danych, aby wymusić rollback.

API otrzymuje wyłącznie wąskie EXECUTE lifecycle/read/source guard; nie ma bezpośredniego SELECT/DML tabel Nemesis, capability lub release registry. SECURITY DEFINER ma search_path pg_catalog,pg_temp oraz jawne REVOKE PUBLIC. Internal trigger kończący deferred slot invariants także ma własne definer prawa, ponieważ działa po powrocie funkcji podczas commit. Role AI/motivation/retention nie zyskują dostępu do prywatnej historii Nemesis.

calorie_app_nemesis_worker jest osobną bazową rolą NOLOGIN, NOINHERIT, bez superuser/create/bypassrls i niepotrzebnych memberships. Migracja przed DDL odrzuca outgoing memberships bazy, niebezpieczne znane incoming roles i nadmierne efektywne prawa członków LOGIN, także table/column/SECURITY DEFINER ACL. Osobny SCRAM LOGIN dziedziczy tylko tę rolę. Może wykonać app.e8n_maintain(batch), nie accept, zmienić zgód lub naliczyć wynik. Faza C testuje jawny prywatny bootstrap; faza I podłączy właściwy provision i zweryfikuje rzeczywiste LOGIN, column grants oraz efektywne prawa. DATABASE_URL przechowujemy poza Git i logami.

Jedno wywołanie `python -m calorie_app.modules.nemesis.maintenance --batch 100` utrwala wygasłe invited, zakończone active, zwalnia slots i sprząta wygasłe pełne responses/codes/cursors oraz admissions starsze niż maksymalne rolling okno 24 h; minimalne receipts zachowują ochronę przed ponownym naliczeniem. Batch jest w zakresie 1..1000; retry jest bezpieczne. O3 uruchomi to co minutę swoim istniejącym schedulerem po integracji. Komponent nie zakłada, że worker był terminowy: accept/read rozpoznaje DB clock, a accept atomowo zwalnia zakończone poprzednie slots. CLI wypisuje wyłącznie agregowane liczby, nie payloady lub identyfikatory partnerów. Maintenance nie finalizuje wyników; finished pozostaje provisional po deadline.

DB nemesis_control ma enabled=false po migracji. Otwarcie wymaga zgodnej bieżącej installation epoch i odebranej pary projector/finalizer w nemesis_releases, która w migracji Nemesis jest pusta. Nie istnieje produkcyjny env/header/admin fallback lub automatyczna rejestracja. Migrator prywatnej testowej bazy może wstawić fake test pair do prób komponentu; taki fixture jest wyłącznie w tests/support i nie trafia do wheel ani produkcji. E8.4 dostarczy właściwe rewizje i kontrolowaną procedurę odbioru.

Restore wymaga zatrzymanego traffic/workera, nowego losowego sync_epoch i natychmiastowego mismatch z kontrolą Nemesis. Stare mutacje, codes i cursors nie działają; shared statistics jest zamknięte. Migrator wykonuje bounded app.e8n_restore_cancel(batch) aż do anulowania wszystkich poprzednich invited/active/finished. Stare challenge nie odzyskuje sharing ani nowej zgody. Faza I dołączy to do istniejącego chain restore, zachowując bramki motywacji/AI. Nie otwieraj capability przed cancellation i właściwym odbiorem E8.4.

Deletion helper jest wydzielony: app.e8n_delete_helper(owner,operation,purge). Wymaga dokładnego trwałego deletion job, generacji deleting i subject fence; purge dodatkowo potwierdzonej tożsamości i istniejącego transakcyjnego _deletion_context. Nie pobiera peer account po challenge locks. Begin odcina access przy state/generation przed purge; purge usuwa owner receipts/admissions/codes/cursors, prywatne bindings i snapshots peer receipts, pozostawiając bezpieczny cancelled/deleted marker drugiej stronie. Wrapper E8.1+2→E7→E6→E4 nie jest zmieniony w fazie C; integracja ma go zachować w całości, wraz z cleanup intents i anonimowymi AI counters.

Obserwowalność używa request_id, kodu odmowy, liczby transitions/pruned i zagregowanego backlog. Nie zapisuje body, Authorization, kodów, pseudonimów, partner danych lub source rows. Własne testowe e8n_clock zastępuje migrator tylko w prywatnej bazie; runtime caller nie ustawia czasu. Lokalny PG i syntetyczny JWT nie zastępują właściwej produkcyjnej konfiguracji Keycloak/HTTPS lub CI.

Do odtworzenia prywatnych prób ustaw E8_3_POSTGRES_CREDENTIALS na plik JSON własnego klastra z admin_url, migrator_url, api_url i worker_url; nie publikuj jego treści. Poison role tests wymagają oddzielnego klastra i E8_3_ROLE_AUDIT_CREDENTIALS, aby nie mutować globalnych ról innych testów. TCP probe ma osobne własne porty przez E8_3_HTTP_PROBE_PORT_BASE. Bootstrap jest wyłącznie w tests/support/e8_3_postgres.py. Faza I ma włączyć te dowody do właściwego CI na jego usługach; lokalny secret file nie jest konfiguracją GitHub Actions.
