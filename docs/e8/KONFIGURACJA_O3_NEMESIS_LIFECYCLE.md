# Konfiguracja Nemesis lifecycle dla O3 - osoba 2

12 października 2026. Integracja E8.3-I podłącza produkcyjne main, readiness, provision, source projection, restore i purge na jedynym head `0020_e8_nemesis_integration`. Stan publikacji i wykonane kontrole określają raport oraz recenzja. Instrukcje nie potwierdzają wykonania O3, wdrożenia lub aktywacji E8.4.

Opublikowana w draft PR #37 migracja 0018_e8_nemesis_lifecycle rozszerza odebraną granicę upstream 0017_e8_purge_commit z b2c6709 po 0016_e8_motivation. Wcześniejsze próby 0016→0017 Nemesis są wyłącznie prototypem, nie odbiorem tej nowej linii. Migracja nie importuje zmiennego runtime. Koordynator potwierdził finalny numer/parent i przyjął dokładny source b2c6709 przed pierwszym pushem. Pusta i wypełniona linia przeszła rzeczywiste próby PG17 autora i nieautora; szczegóły oraz zakres fazy C są w raporcie i recenzji. Downgrade z historią, minimalnymi receipts, admissions, codes, slots lub cursor odmawia atomowo przed DDL. Nie usuwamy tych danych, aby wymusić rollback.

API otrzymuje wyłącznie wąskie EXECUTE lifecycle/read/source guard; nie ma bezpośredniego SELECT/DML tabel Nemesis, capability lub release registry. SECURITY DEFINER ma search_path pg_catalog,pg_temp oraz jawne REVOKE PUBLIC. Internal trigger kończący deferred slot invariants także ma własne definer prawa, ponieważ działa po powrocie funkcji podczas commit. Role AI/motivation/retention nie zyskują dostępu do prywatnej historii Nemesis.

calorie_app_nemesis_worker jest osobną bazową rolą NOLOGIN, NOINHERIT, bez superuser/create/bypassrls i niepotrzebnych memberships. Migracja przed DDL odrzuca outgoing memberships bazy, niebezpieczne znane incoming roles i nadmierne efektywne prawa członków LOGIN, także table/column/SECURITY DEFINER ACL. Osobny SCRAM LOGIN dziedziczy tylko tę rolę. Może wykonać app.e8n_maintain(batch), nie accept, zmienić zgód lub naliczyć wynik. Właściwy `infra/local/provision_nemesis_worker.py` wymaga PG17, jednego head0020, prywatnych ACL docelowej bazy i bezpiecznej sesji. Tworzy własny oznaczony SCRAM LOGIN z membership INHERIT TRUE, SET FALSE, ADMIN FALSE. Zmienne NEMESIS_WORKER_LOGIN/NEMESIS_WORKER_PASSWORD przekazujemy wyłącznie przez środowisko; admin używa kontrolowanej konfiguracji PG*. Worker ma USAGE app, odczyt Alembic metadata i EXECUTE e8n_maintain, bez surowych tabel, restore lub control. Provisioning odmawia niebezpiecznej istniejącej tożsamości i dostępu do innych baz aplikacyjnych/Keycloak. DATABASE_URL oraz hasła przechowujemy poza Git i logami.

Jedno wywołanie `python -m calorie_app.modules.nemesis.maintenance --batch 100` utrwala wygasłe invited, zakończone active, zwalnia slots i sprząta wygasłe pełne responses/codes/cursors oraz admissions starsze niż maksymalne rolling okno 24 h; minimalne receipts zachowują ochronę przed ponownym naliczeniem. Batch jest w zakresie 1..1000; retry jest bezpieczne. O3 uruchomi to co minutę swoim istniejącym schedulerem po odbiorze integracji. CLI wymaga dokładnego head0020 oraz PG17; nie tworzy harmonogramu ani nie wykonuje migracji. Komponent nie zakłada, że worker był terminowy: accept/read rozpoznaje DB clock, a accept atomowo zwalnia zakończone poprzednie slots. CLI wypisuje wyłącznie agregowane liczby, nie payloady lub identyfikatory partnerów. Maintenance nie finalizuje wyników; finished pozostaje provisional po deadline.

DB nemesis_control ma enabled=false po migracji. Otwarcie wymaga zgodnej bieżącej installation epoch i odebranej pary projector/finalizer w nemesis_releases, która w migracji Nemesis jest pusta. Nie istnieje produkcyjny env/header/admin fallback lub automatyczna rejestracja. Migrator prywatnej testowej bazy może wstawić fake test pair do prób komponentu; taki fixture jest wyłącznie w tests/support i nie trafia do wheel ani produkcji. E8.4 dostarczy właściwe rewizje i kontrolowaną procedurę odbioru.

Restore wymaga zatrzymanego ruchu i workerów oraz istniejącej procedury instalacji nowej losowej sync_epoch, która natychmiast powoduje mismatch z kontrolą Nemesis. Stare mutacje, codes i cursors nie działają; shared statistics pozostają zamknięte. Na head0020 migrator uruchamia `python -m calorie_app.modules.nemesis.restore --batch 100`, po jednej bounded partii, aż pending=0. Wywoływana owner-only `app.e8n_restore_maintain(integer)` wymaga disabled gate oraz mismatch epoki, anuluje stare invited/active/finished i usuwa stare pełne responses, codes oraz cursors. Minimalne receipts i admissions pozostają; sharing oraz zgody nie wracają. CLI nie rotuje wspólnej epoki, nie otwiera capability ani nie zastępuje wcześniejszych etapów restore motywacji/AI. Nie otwieraj capability przed zakończeniem cleanup i odbiorem E8.4.

Deletion helper jest wydzielony: app.e8n_delete_helper(owner,operation,purge). Wymaga dokładnego trwałego deletion job, generacji deleting i subject fence; purge dodatkowo potwierdzonej tożsamości i istniejącego transakcyjnego _deletion_context. Nie pobiera peer account po challenge locks. Begin odcina access przy state/generation przed purge; purge usuwa owner receipts/admissions/codes/cursors, prywatne bindings i snapshots peer receipts, pozostawiając bezpieczny cancelled/deleted marker drugiej stronie. 0020 opakowuje produkcyjne begin/purge, zachowując pełny łańcuch E8.1+2→E7→E6→E4, cleanup intents i anonimowe AI counters. Wewnętrzne rodzice *_e8_19 i e8n_delete_helper nie mają EXECUTE operatora. Exact confirmed scope ustanawia definer purge, który bierze account/counter i global community/AI przed challenge locks; nie pobiera peer account po challenge. Confirmation pozostaje bez zmian. Minimalny operator używa istniejących publicznych funkcji, bez raw context lub tabel.

Obserwowalność używa request_id, kodu odmowy, liczby transitions/pruned i zagregowanego backlog. Nie zapisuje body, Authorization, kodów, pseudonimów, partner danych lub source rows. Własne testowe e8n_clock zastępuje migrator tylko w prywatnej bazie; runtime caller nie ustawia czasu. Lokalny PG i syntetyczny JWT nie zastępują właściwej produkcyjnej konfiguracji Keycloak/HTTPS lub CI.

Do odtworzenia prywatnych prób ustaw E8_3_POSTGRES_CREDENTIALS na plik JSON własnego klastra z admin_url, migrator_url, api_url i worker_url; nie publikuj jego treści. Poison role tests wymagają oddzielnego klastra i E8_3_ROLE_AUDIT_CREDENTIALS, aby nie mutować globalnych ról innych testów. TCP probe ma osobne własne porty przez E8_3_HTTP_PROBE_PORT_BASE. Trzeci obowiązkowy plik E8_3_PARENT_DELETION_CREDENTIALS zawiera operator_url minimalnego rzeczywistego deletion LOGIN na tej samej source bazie. Niepełny zestaw trzech plików jest błędem. Bootstrap jest wyłącznie w tests/support. Czyste CI przygotowuje dwie własne labeled Docker PG17 services i uruchamia hardened producer operatora; helper usuwa odziedziczone PG* i ustawia zaufany source target, a po teście przywraca ENV i usuwa wyłącznie własne kontenery. Mocki nie są dowodem Linux Docker — ten zakres wymaga rzeczywistych jobów. Lokalny secret file nie jest konfiguracją GitHub Actions.
